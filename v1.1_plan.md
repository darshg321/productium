# Productium v1.1 plan

Goals:

1. **The AI can fix situations the app's structure doesn't fit (Part A).** Real life doesn't always follow the
   app's categories (activities, weekly periods, day changes, settings). The AI should be able to change what the
   app actually does in those cases without code written for each one, while staying safe, previewable and
   undoable.
2. **Proper GUI and data testing on a real iPhone (Part B).** Every screen and every kind of data is exercised on a
   physical iPhone plugged into this Linux machine, not just the Linux core tests and a simulator compile.
3. **Fix alarms and Screen Time (Part C).** Alarms don't seem to fire at the right times, and Screen Time you've
   provided doesn't show up in Highlights or Your Week.
4. **Leaner prompts and no-approval learning (Part D).** Cut the system prompts down to what changes behaviour.
   Replace the approval-gated Opus reflection with Sonnet: it writes the recaps and insights and quietly learns
   about you. What it learned and changed is visible in Settings, but there's no approval step and no
   announcement.
5. **Free Apple ID only (Part E).** Remove all code that needs a paid Apple Developer account, so there's one build,
   one project spec and one install path. What a paid account would add or simplify is written down in `DESIGN.md`
   §14, so it can come back later.
6. **Rewards that work on the brain (Part F).** Research the reward mechanisms apps use (YouTube Studio's confetti
   for creators, progress rings, milestones, surprise) and use the ones with evidence behind them throughout the
   app. They reward what you're trying to do, never opening Productium itself.
7. **Life Metrics dashboard (Part G).** One screen like a company sales or software dashboard: scrolling minutes,
   pickups, first pickup, sleep, focus minutes, mood, steps and more. Each one has a green or red arrow against the
   previous day, week or month, and a chart, so you can see whether things are actually getting better.
8. **Use the sensors the app already has access to (Part H).** Steps, daylight and resting heart rate are read but
   never used. Pickups aren't captured at all.
9. **A simpler Schedule screen (Part I).**
10. **Works in grayscale (Part J).** Every screen has to make sense with iOS's grayscale colour filter on.

Overall order: **E first** (it shrinks what B has to sign and test), then B1–B6, C, D, H, G, I, F, A, then the
rest of B. J's rules apply to every screen built from H onwards. J's audit runs last, over the whole app.

Status at the start: v1.0.x released, 169 core tests green, `App/` is only compiled on CI (simulator, unsigned) and has
never been tested automatically. See `DESIGN.md` §13.

## Part A: Give the AI power over the planner's inputs

### A.0 Principle

Today the AI's power is limited to the app's categories: activity fields, `weekdays`, `day_change`, the four
behaviour settings. Anything outside them (A/B days, sick weeks, a trip, a teacher moving a class) needs new code.

But every day is worked out into the same few planner inputs (`Planner.swift:160-225`):

- wake, bedtime, wind-down
- **busy** times (commitments + buffers, events, routines, dinner, locked blocks)
- **fixed** blocks shown on the timeline
- **free** windows, **capacity** (`capacity × loadFactor × policy.capacityMultiplier`), free-time target
- tasks waiting for time (deadlines, estimates, priority)

Nudges, Friction (scrolling) and flashcards each have a similarly small set of inputs. That set is everything the app
can do differently. **If the AI can override any of those inputs, over any span of days, with a reason, it can
express any situation the app could act on.** Coverage is complete because the targets are the engines' inputs, not
a list of predicted cases.

### A.1 `DayRule`: which days something applies to

Replace `weekdays: Set<Int>` on `Commitment` and `ActivityPeriod` with `when: DayRule`. The current check is
mostly in `Commitment.applies(on:)` (`Models.swift:171`), but `weekdays` is used about 53 times across 14 files, so
this is a real migration.

```swift
indirect enum DayRule: Codable, Hashable, Sendable {
  case weekdays(Set<Int>)
  case dates(from: Date?, until: Date?)
  case on([Date]), except([Date])
  case dateParity(odd: Bool)
  case weekParity(anchor: Date, odd: Bool)          // alternating weeks
  case nthOf(sequence: String, mod: Int, eq: Int)   // A/B days, 6-day rotations
  case label(String)                                // "exam-week", "half-day", "no-school"
  case all([DayRule]), any([DayRule]), not(DayRule)
}
```

- **Sequences:** named, counted sets of days, e.g. `school = weekdays 2–6 AND NOT label(no-school)`, anchored on a
  date. A/B days are `nthOf("school", 2, 0|1)`. A cancelled school day stops being counted, so every later day in
  the rotation shifts by itself.
- **Labels:** named sets of dates. `day_change` with `cancelled` on school also adds the `no-school` label.
- **Migration:** existing `weekdays` lists load as `.weekdays(...)`. Export format bumps; the old format still loads.
- **Evaluator:** `DayRule.matches(day, context)` is pure and lives in ProductiumCore. It's cached per planning run.

### A.2 `Situation`: overrides on the planner's inputs

```swift
struct Situation: Codable, Identifiable {
  var id: UUID
  var said: String                 // the student's own words
  var scope: DayRule
  var effects: [Effect]
  var expires: Date?
  var source: Writer               // student | box | reflection
  var createdAt: Date
}
enum Effect: Codable {
  case busy(start: TimeOfDay, end: TimeOfDay, title: String)
  case free(start: TimeOfDay, end: TimeOfDay)                 // remove what the timetable says is busy
  case replace(commitment: UUID, with: [BlockSpec])           // swap a day's periods
  case setInput(path: String, value: JSONValue)              // "planner.capacity", "routines.to_school.minutes", "wake"
  case hold(item: UUID), boost(item: UUID)                    // pause or prioritise a task
  case mute(nudges: NudgeKind?)
  case note(String)
}
```

- The planner applies situations **last**, after commitments, events and routines, as one final pass per day.
  Nudges and Friction read the same resolved day.
- `DayException` becomes one kind of situation. `day_change` stays in the Registry as a shortcut and is stored as
  a situation.
- Valid `setInput` paths come from the Registry, each with its type and range, so the AI can't make one up.
- Examples the tests should cover:

| Situation | How it's expressed |
|---|---|
| A/B days | `replace(School, A periods)` scoped to `nthOf(school,2,0)`, and the same for B |
| Sick for 3 days | `mute(nil)`, `setInput(planner.capacity, 0)`, `expires` |
| Grandma visiting | `busy` on Sat/Sun, `setInput(planner.freeTimeMultiplier, 1.3)` |
| Ankle sprain, driven to school | `setInput(routines.to_school.minutes, 10)` for 7 days |
| Exam week | label `exam-week`, `setInput(planner.maxBlockMinutes, 45)` |

### A.3 Rules about what can't be broken, instead of per-field permissions

Replace most per-field permission checks with invariants checked in code **on the resolved plan** after the change:

- no sleep below `sleepFloorMinutes`; never change sleep need, floor or trade-offs unless the student says so
- never overwrite student-written data or `(you)` about-me lines
- `setInput` values stay within the Registry range and maximum step
- deadlines and estimates only move when the student's own words say so
- Calendar (`cal`) events stay read-only

How a change gets applied depends on how much it affects and how easily it's undone, not on its type:

| Change | Applied how |
|---|---|
| Ends within ~14 days, or has an `expires` | applied at once, with Undo (box / Sonnet) |
| Open-ended or recurring, but describes facts (a timetable, a rotation) | applied at once, with Undo and a clear receipt |
| Open-ended change to how the app behaves (settings, nudges, capacity) | only the Sonnet insight pass (D.2), applied quietly within ranges and maximum steps, listed in Settings with Revert |
| Breaks an invariant | refused, with the reason in the receipt |

### A.4 Show the effect, not the edit

- `Preview.diff(state, change, days: 7) -> [DayDiff]`: plan with and without the change and compare. This is the
  receipt for every situation and DayRule change: "Tue: Bio 9:00 → 10:30 · study 90 → 45 min · no reminders".
- **Let the AI check before it commits:** add an `expand` / `preview` tool to the box call. The AI can ask "what does
  this rule give for the next 10 school days?" before it answers. This turns the box into a short tool-use loop:
  at most 2 preview calls, then commit. The budget is counted in `Usage`.
- The Settings → What Productium Thinks → Changes log shows the same diff for each change the insight pass made.

### A.5 Fallbacks and learning from them

- **Notes the app can't act on:** if something matters but changes no input ("my parents take my phone at 10"), it's
  saved as a situation with only a `note` effect. Active notes go into every AI context.
- **Gap log:** when the AI wanted an effect that doesn't exist, it writes `gap: {said, wanted}`. It's shown in
  Settings → What Productium Thinks and in the export, and becomes the backlog for v1.2.
- **Turning repeats into structure (Sonnet insight pass, D.2):** it looks for situations that keep coming back and
  makes them permanent, e.g. 9 "B day" overrides become a rotation. This is applied quietly and logged in Settings
  with Revert, like every other insight-pass change.
- **Conditional overrides:** the four behaviour settings become `when: DayRule → set` overrides with the same
  ranges and maximum steps, e.g. capacity 0.8 on Fridays, 45-minute blocks in exam week. Only the insight pass
  writes them.

### C.1 Alarms aren't scheduled at the right times

There are two separate alarm paths. Both are rescheduled on **every** `replan()` (`AppModel.swift:188` and `:198`)
from fire-and-forget `Task { … }`s:

- **Wake alarms** (`integrations.alarms`, `AlarmService.schedule`, `SystemServices.swift:22`): cancel every saved id,
  then schedule the next 3 `wakePlans` with new UUIDs and save the ids under `alarm.ids`.
- **Nudge alarms** (`prefs.nudges.alarms`, `NudgePlanner.alarms` at `Nudges.swift:344` → `AlarmService.scheduleNudges`):
  bedtime, time to leave, and 10 minutes into an unstarted study block. They're limited to `horizon` and at most 6,
  and kept under `SharedConfig.Key.alarmIds`.

Suspects to check:

1. **Overlapping reschedules.** Two replans close together start two schedule tasks. Both read the old ids before
   either saves, so one set of alarms is never cancelled (duplicate or stale alarms), or a newer plan is
   overwritten by an older one. Same read-modify-write problem on `savedNudges` across `await`s. Fix: one
   serial scheduler (an actor) that keeps only the latest request and compares with what's actually on the device
   (`AlarmManager.shared.alarms`) instead of saved ids.
2. **Unstable keys.** `miss.\(b.id)` and `bed.\(s.id)` depend on block ids staying the same across replans. If study
   or sleep blocks get new ids, alarms are cancelled and rescheduled, or orphaned. Check `stableId` for study
   blocks, and key on (kind, day, start) where that's what matters.
3. **Horizon and app not opened.** Only alarms inside `horizon`, at most 6, are scheduled, and only when the app
   replans. Without a foreground or background refresh, later alarms never get scheduled. Check `BackgroundRefresh`
   and whether the next wake alarm always exists.
4. **Which plan.** Wake alarms use `plan.wakePlans` (today only if wake is still ahead). Check day changes, sleep-in
   (`wake` alone), `autoWake` from the first class, and DST / time zone (`Calendar.current` vs the app's `cal`).
5. **Two toggles.** "Wake-Up Alarms" (`integrations.alarms`) and "Alarms for the Important Ones"
   (`prefs.nudges.alarms`) are separate settings, and the box can only set the second. Make sure the UI is clear
   about which one does what, or merge them.
6. **Fallback without AlarmKit** (before iOS 26.1): only wake alarms fall back to notifications, and nudge alarms
   do nothing. The notification fallback also can't break through Focus once time-sensitive delivery goes (Part E),
   so check whether AlarmKit is actually being used on the phone (iOS version, authorization).

### C.2 Screen Time doesn't appear in Highlights or Your Week

The Review screen's Screen Time card (`ReviewView.swift:129`) averages `DayTotals.screen` for the last 7 days. That
comes from `state.screen` for each day (`AppModel.dayInputs` → `Insights.dayTotals` → `distractingMinutes`). Suspects:

1. **Week-view screenshots never reach Review.** A screenshot of the week or daily-average view goes to
   `state.screenAverages` only (`DumpApplier.swift:524`). Review, Your Week and the planner never read
   `screenAverages`, so it's saved but never shown. Fix: show it in Highlights ("daily average from Screen Time"),
   and spread it over the days it covers when there's no per-day data.
2. **Wrong date.** A day screenshot's date comes from `dateLabelShown` ("today" / "yesterday") or `a.date`. If the
   model gives a weekday name ("Monday") or nothing, `day(a.date)` may land on the wrong day or outside the 7-day
   window. Add weekday-name handling, and say in the receipt which date it was saved for.
3. **Overwritten by measured data.** `syncScreen` (`AppModel.swift:592`): `Friction` estimates from Shortcuts are
   merged in, and on the paid build `ScreenTimeService.usageDays` replaces any day where it has distracting
   minutes > 0, including a screenshot day, using `byDay[d.day]` without `startOfDay`. Part E removes the
   `ScreenTimeService` half. For the rest, screenshots should always win over Shortcuts estimates.
4. **Scrolling list.** `distractingMinutes` only counts apps marked as scrolling. A screenshot of apps not in the
   list shows 0 minutes. That's correct, but Highlights should then say "0 min of scrolling (3h 22m total)"
   instead of looking empty. The total should be shown too.
5. **Your Week** (`WeekAsLived`): check that it actually draws screen time for a day, and that the timeline segments
   include it.
6. **Old data.** The 2026-11-17 backup has one screen day whose `distractingMinutes` (68) doesn't match its apps
   (Instagram 96 + Discord 35 = 131). Recompute on load (`recomputed(scrollingApps)`), not only when the list
   changes.

## Part D: Leaner prompts and quiet learning with Sonnet

### D.1 Cut the system prompts to what changes behaviour

Every system prompt starts with `Prompts.persona` (`AI.swift:321`), and the box prompt (`DumpPrompt.swift:51`) adds
about 50 lines plus `Registry.promptText()`.

- **Remove lines that don't affect what the app does**, e.g. "No diagnoses; if someone seems in distress, suggest
  a trusted adult or a helpline." Keep only rules whose removal would change outputs the app uses. (The
  `Wellbeing.crisisText` shown in the app's interface isn't part of any prompt and costs no tokens. It's a separate
  decision.)
- **Remove repeated or outdated rules**: anything the response format already enforces, explanations of how the app
  works that the model doesn't need to act, and the "isn't yours to change / suggestion the student approves" lines
  that D.2 makes wrong.
- **Per-feature persona**: the box, flashcards and reads don't need the same tone and sleep lines. Keep a one-line
  persona only where the reply is shown to you.
- **Measure, don't guess**: system prompts are byte-identical so the server caches them (`AI.swift:319`). Cached
  input is cheap, so most of the saving is on cache misses and output. Record input / cached / output tokens per
  feature from `callLog` before and after.
- **Check quality**: `scripts/inbox-eval` and the replay set (B4) must give the same operations before and after
  every cut.

  - remove the Opus route, the approval states (`pending` / `rejected` / `expired`) and the reject-pause

## Part F: Rewards that work on the brain

### F.0 Principle

Apps like YouTube Studio (confetti when a video beats its usual numbers), Duolingo, Asana and Apple Fitness are built
to make some actions feel rewarding. Productium can use the same mechanisms for what you're trying to do:

- starting and finishing focus
- going to bed on time
- closing a scrolling app early
- finishing a task, or the day's plan
- a metric improving

Three rules:

- **Never reward using Productium itself.** No rewards for opening the app, time spent in it or checking it. The
  goal is less phone time, so engagement-maximising tricks are off limits.
- **No punishment.** No sad animations, no loss-framed streaks, no "you broke your streak". This keeps `DESIGN.md`
  §11's "no streaks, no scores, no shame", and F.1 checks the evidence for it.
- **Everything is evidence-backed.** Every mechanic links to its evidence line in `DESIGN.md` §12, along with
  whether that evidence has replicated.

### F.1 Research first

The candidates below were written from memory. Web search was unavailable when this part was written, so **F1
checks each citation and whether it replicated before anything is built on it.** Some may be wrong or weaker than
they're listed here. F1 also looks for mechanisms not on this list, especially from game design (juice, feedback
loops) and from how YouTube, Duolingo, Strava, Apple Fitness and Headspace celebrate.

| Mechanism | Evidence to check | How Productium would use it |
|---|---|---|
| Surprise is worth more than a predictable reward | reward prediction error (Schultz, Dayan & Montague 1997); motivating-uncertainty effect (Shen, Fishbach & Hsee 2015) | how big a celebration is varies, and a bigger one sometimes comes unannounced (seeded, see F.3) |
| Immediate rewards keep people going | Woolley & Fishbach 2016 / 2018 | the moment Done is tapped, not later in the Weekly Note |
| The end of an experience is what's remembered | peak-end rule (Kahneman et al. 1993) | end each focus session on a high point: what moved, how much is left, the free time that comes next |
| Small visible progress is motivating | progress principle (Amabile & Kramer 2011) | "Moved forward today" list; steps ticking off on the task |
| Effort goes up near a goal | goal-gradient (Kivetz, Urminsky & Zheng 2006) | a ring for the day's plan; "10 min left of today's plan" near the end |
| A head start makes people more likely to finish | endowed progress (Nunes & Drèze 2006) | progress starts above zero ("plan made" counts as the first step) |
| New beginnings restart motivation | fresh start effect (Dai, Milkman & Riis 2014) | Monday / new month / after a break framing, especially after a rough week (already used by `ScreenTaper`) |
| Pairing a chore with something you like | temptation bundling (Milkman, Minson & Volpp 2014); Premack principle | show the free time that study unlocks ("after this: 2h free"); a focus playlist offered when a block starts |
| Tracking progress helps people reach goals | self-monitoring meta-analysis (Harkin et al. 2016) | the Life Metrics dashboard (Part G) is part of the reward system |
| Expected tangible rewards undermine intrinsic motivation; informational praise doesn't | overjustification meta-analysis (Deci, Koestner & Ryan 1999) | no points or coins. Celebrations say what you did ("Bio outline done, 2 days early") |
| Broken streaks make people quit | Silverman & Barasch 2023 | no consecutive streaks. Use counts that can't break ("focused on 14 days this month") and cumulative milestones |
| Unfinished tasks get resumed | Ovsiankina effect holds; the Zeigarnik memory effect doesn't replicate (Ghibellini & Meier 2023) | when you stop, leave the next step named and offer "resume" next time; don't rely on "unfinished tasks nag at you" |
| Milestones | YouTube subscriber / view milestones, Strava personal records (practitioner, not peer-reviewed) | cumulative milestones that keep getting further apart (10, 25, 50, 100 focus hours) and personal bests (lowest scrolling week, most regular sleep week) |
| Feedback through several senses | HIG / game-feel practice (practitioner) | haptics (`.sensoryFeedback`), motion, optional sound. These matter more than colour in grayscale (Part J) |
| Grayscale makes the phone less rewarding | grayscale studies (e.g. Holte & Ferraro 2020; Dekker & Baumgartner 2023) | the reverse direction: a Shortcuts recipe that turns grayscale on when a scrolling app opens and off when it closes, if Shortcuts' colour filter action allows it (check) |
| Identity messages ("be a reader") | Bryan et al. 2011; failed replication (Gerber et al. 2016) | **don't** rely on it |
| Comparing yourself with others | upward social comparison harms teens (check sources) | **don't**: comparisons are only with your own past |

### F.2 Where rewards go

| Moment | Reward | Intensity |
|---|---|---|
| Focus Done / Got Some Done | haptic + check animation + what moved ("Essay 40% → 65%") + what's next / free time unlocked | small, sometimes medium (surprise) |
| Task or step done | check animation, remaining steps shown, ring fills | small |
| Day's plan finished | confetti + one line ("All of today's plan done. 3h free from now") | big, at most once a day |
| In bed by the planned time | next morning: a one-line card "In bed on time, 8h 40m sleep" | small |
| Closed a scrolling app early (`Friction` closed before the median session) | quiet notification: "Back in 6 min, 4 min shorter than usual" | small, ≤3 a day |
| A metric turns green for the week (Part G) | the tile pulses once on the dashboard, and the win goes into the Weekly Note | medium |
| Milestone or personal best | confetti + a card that says what the record is | big, rare by design |
| Weekly Note | wins come first, with records and "better than last week" items from Part G | none (no animation) |

### F.3 How it's built

- **Core `Rewards` engine** (ProductiumCore, deterministic, tested). It turns an event (focus ended, item done, plan
  finished, bedtime kept, scroll closed early, metric flipped, milestone) into `RewardMoment{kind, intensity,
  copy}`, or into nothing.
  - **Rarity budget:** at most 1 big moment a day and a few medium ones a week. Celebrations that fire on every tap
    stop working (habituation).
  - **Surprise:** whether a small moment becomes medium is random, but seeded per day, so tests are reproducible.
  - Copy comes from data: what moved, by how much, and what's next. No generic "Great job!".
  - It can never fire on app open, on a tab change or on time spent in Productium. A test checks this.
- **UI components:** confetti (SwiftUI `Canvas` particles, no dependency), check / ring animations, haptics, and an
  optional short sound. **Reduce Motion** swaps confetti for a fade plus a haptic.
- **Setting:** Celebrations Full / Subtle / Off (Settings → Notifications or its own row). Default Full.
- **Measure whether it works:** log every `RewardMoment` and what happened next (next focus started within 24 h,
  tasks finished, scrolling that evening). After 4 weeks the insight pass (D.2) compares days with and without
  medium/big moments. If celebrations don't change anything for you, it turns intensity down (within a range, logged
  in the Changes log like any other insight change).

## Part G: Life Metrics dashboard

### G.0 What it is

One screen that works like a sales or software metrics dashboard, but for your life. Each metric is a tile with:

- today's / this week's / this month's value
- an arrow showing which way it moved compared with the previous period
- a colour for whether that's good: green when it moved the right way, red when it moved the wrong way, gray when
  the change is within normal day-to-day noise
- a sparkline

Tapping a tile opens a detail chart. The goal is to see whether things are actually improving, not to grade you.
There's no overall "life score" (§11).

**Where it lives:** the Review tab becomes the dashboard, with the Weekly Note at the top and Your Week at the bottom.
The Highlights cards are replaced by metric tiles. This keeps five tabs (a sixth would push one into iOS's "More").
A Day / Week / Month control at the top sets the comparison period.

### G.1 Metrics

| Metric | Better when | Source (best first) |
|---|---|---|
| Scrolling minutes | lower | screenshots, `Friction` sessions, estimates |
| Total screen time | lower | Screen Time screenshots |
| Pickups | lower | Screen Time screenshots (Part H) |
| First pickup | later, or after wake + a set gap | screenshots |
| Scrolling app opens | lower | `Friction` (measured on the phone) |
| Notifications received | lower | screenshots |
| Sleep | inside the need range (closer is better; too much isn't "better") | HealthKit, check-ins, motion, plan (`SleepEstimator`) |
| Bedtime / wake regularity | lower spread | same |
| In bed on time | more days | plan vs sleep |
| Focus minutes (productive) | higher, up to the plan | `WorkDone.minutes` |
| Plan done | higher % | `WorkDone` vs plan |
| Tasks finished, finished early | higher | items |
| Mood, energy | higher | `MoodEntry`, Health State of Mind (Part H) |
| Steps | higher | HealthKit / `CMPedometer` |
| Daylight minutes | higher | HealthKit |
| Time out of the house | higher | places / visits |
| Resting heart rate | lower (detail only, not a headline tile) | HealthKit |

You choose which tiles show and in what order (edit mode, like iOS widgets). The defaults are scrolling, pickups,
sleep, focus minutes, mood and steps.

### G.2 Comparisons and arrows

- **Periods:** today vs yesterday, this week vs last week, this month vs last month. Until a period is over it's
  compared **like for like**: Wednesday so far vs last week Monday to Wednesday, and today until 3pm vs yesterday
  until 3pm. Otherwise every metric looks bad in the morning.
- **Verdict:** `better` / `worse` / `same`. It's `same` (gray) when the change is within the metric's noise band
  (e.g. less than half the standard deviation of the last 4 weeks, or below a minimum like 5 min). This stops random
  variation from turning tiles red.
- **Missing data** is never counted as zero. A period with too little data shows "Not enough data" instead of an
  arrow. Each value says where it came from (measured / screenshot / estimated) and how many days it covers.
- **Grayscale (Part J):** the arrow only shows direction. Good or bad is also shown by the symbol (filled
  `checkmark` vs `exclamationmark`) and a word ("better" / "worse" / "same"), never by colour alone.

### G.3 Detail screen

- Swift Charts: daily bars or a line, a 7-day rolling average, the previous period drawn faintly behind, and a
  goal / target line where there is one (e.g. the `ScreenTaper` limit, sleep need).
- Range: 1 week, 1 month, 3 months, all time.
- **Annotations:** situations (A.2), insight-pass changes (D.2) and milestones (F) are marked on the chart, e.g. "bedtime
  moved 20 min earlier". You can then see whether a change helped.
- **Noticed together:** simple within-person relationships computed in core, e.g. "On days with 8h+ sleep you did
  35 more focus minutes". Shown only with 14+ days of data and a minimum effect size, and worded as "noticed", not
  as a cause.

## Part H: Use more of the phone's sensors

### H.0 What's unused today

- `HealthService` already reads **steps, daylight and resting heart rate**. They're stored in `HealthDay`
  (`DayTotals.steps` exists too), but no view or engine uses them. Only sleep is used.
- **Pickups / phone opens:** not captured. There's no public API for unlock count without DeviceActivity, which
  needs a paid account (Part E, `DESIGN.md` §14). On a free account there are three usable sources:
  1. Screen Time screenshots show **Pickups**, **First Pickup**, pickups per app and **Notifications**. The
     `screen_time` entity doesn't have fields for them yet.
  2. `Friction` counts every opening of a scrolling app it sees through Shortcuts. These are measured, not
     estimated.
  3. Shortcuts automations Productium already uses as proxies (charger, alarm, Focus).
- **Motion:** only `CMMotionActivity` is used. `CMPedometer` (steps and floors on the phone itself, no Health
  permission, 7 days back) isn't.
- **Mood:** HealthKit's State of Mind (iOS 18) can be both written and read. It isn't used.

### H.1 What each new signal is for

| Signal | Used for |
|---|---|
| Pickups, first pickup, notifications (screenshots) | Metrics tiles (G). First pickup as a wake-time sample for `SleepEstimator` (a lower bound on wake). Pickups per hour go to the insight pass (e.g. heavy pickups during study blocks → a nudge or friction suggestion) |
| Scrolling app opens (`Friction`) | Metrics tile; shows on days without screenshots; calibrates against screenshot pickups |
| Steps (Health, else `CMPedometer`) | Metrics. `GapDetector`: steps in a gap explain it ("out walking") instead of asking. Sleep: steps during the estimated night mean you were awake. A movement break suggestion after ~90 min of study with no steps |
| Daylight | Metrics. A morning daylight nudge on free days (circadian evidence to check in F1-style). Insight pass relationship with sleep timing |
| Resting heart rate (and HRV, if added) | Detail only. The insight pass may treat a clear spike plus short sleep as a reason to plan lighter (a conditional override within the A.5 ranges). No health claims in the UI |
| Workouts / exercise minutes (Health) | Explains gaps and activity time. Learns how long practice actually is |
| State of Mind (Health) | Mood logged in Productium is written to Health. Mood logged elsewhere (e.g. Apple Watch) is read in |
| Time at home vs out (visits / places) | Metrics tile. Explains gaps |
| Charging overnight (Shortcuts charger automation, already a `lockProxy`) | One more sleep start signal |

- Every new read type is added to the HealthKit permission request and the export's permission snapshot. Each one
  is optional: if it's denied, that tile shows how to turn it on and nothing else changes.
- Check in B1 / E whether Focus status (`INFocusStatusCenter`) works with free signing. If it does, being in a
  Focus is a useful signal for the gap detector and nudges. If it doesn't, it goes in `DESIGN.md` §14.

## Part J: Works in grayscale

### J.0 Why

Grayscale (Settings → Accessibility → Display & Text Size → Colour Filters) is a common way to make a phone less
tempting, and it's evidence-backed (see F.1). The app currently relies on hue to tell categories apart:

- blue focus, orange free, indigo sleep, gray fixed, purple scrolling, red attention
- the coloured dots on the day chips
- red for today
- meter colours and the `IconTile` squares

In grayscale, blue, indigo and purple become nearly the same dark gray, and the Part G arrows would be unreadable if
only colour separated green from red. The iOS grayscale filter doesn't seem to turn on "Differentiate Without
Colour" (check), so the app can't detect it. **Every screen has to work in grayscale all the time.**

### J.1 Rules (apply to every new screen from H onwards, and to the old ones in J2)

- **Never colour alone** (WCAG 1.4.1). Every category has a symbol and/or a word: `pencil.line` for study, `moon`
  for sleep, `sun` / free label for free time, `hourglass` for scrolling, `flag` for due, `exclamationmark` for
  attention.
- **Good / bad** is shown by symbol shape and a word as well as green / red (G.2).
- **Different lightness** for categories that sit next to each other (timeline, strips, charts): pick system colours
  or tints so adjacent categories differ clearly in luminance, and use fill vs outline, or a hatch pattern for
  estimated / inferred time.
- **State by shape:** selected / today / done shown by fill, weight or a checkmark, not by a colour change only.
- **Celebrations (F)** rely on motion, scale and haptics, which work without colour.
- Charts: the previous period is dashed, not a lighter colour only; targets are labelled lines.

## Risks and open questions

- **Signing:** a free Apple ID may not allow an extra UI test runner app or developer services long-term. With the
  paid code removed (Part E), there's no paid fallback in the plan. If B1 fails, pick between UI-level automation
  that needs no runner (screenshots + accessibility via developer services) and a paid account just for testing
  (see `DESIGN.md` §14).
- **Removing paid features is a real loss:**
  - measured Screen Time and app shields
  - time-sensitive notifications that break through Focus
  - widgets and Live Activities

  The code stays in git history (tag the last commit that has it, E1), and `DESIGN.md` §14 says how to bring it
  back.
- **iOS 17+ tunnel** needs root on Linux (`tunneld`). Fine for a local script, but note it in the script's checks.
- **The box getting more expressive** could make it worse on simple messages. Watch `inbox-eval` scores and token
  use before and after A5 and A7.
- **Effect list completeness:** A.2's effects are the inputs as of today. If an engine gains an input, it needs an
  Effect / `setInput` path. Make the Registry the only place these are declared, so a missing one is a compile or
  test failure.
- **Situations piling up:** expired ones are archived, not deleted (kept for the insight pass); cap how many are
  active.
- **Quiet changes you didn't expect:** with no approval, a bad inference changes the plan without you noticing. The
  safeguards are the small maximum steps, at most 1 change per setting per week, Revert and pins in Settings, and
  a 30-day hold after a revert. If that turns out to be too quiet, add a one-line mention in the Weekly Note,
  not an approval step.
- **Sonnet vs Opus quality** for the insight pass: D6 checks it before the Opus route is removed.
- **Rewards wearing off or backfiring:** celebrations can stop working (habituation) or start to feel patronising.
  The rarity budget, the Subtle / Off setting and F6's 4-week check are the safeguards. Anything that rewards time in
  Productium is a bug.
- **Red tiles discouraging you:** a dashboard full of red after a bad week is the shame §11 avoids. The noise band,
  like-for-like comparisons and fresh-start framing in the Weekly Note reduce this. If it still feels bad, the
  dashboard could show only the comparison with your 4-week average.
- **Screenshot-only metrics:** pickups and notifications exist only on days you send a screenshot. The tiles show
  coverage, and Part H's measured signals (`Friction` opens, steps) fill gaps where they can. Real unlock counts
  need the paid DeviceActivity route (`DESIGN.md` §14).
- **"Noticed together" being read as a cause:** keep the thresholds strict and the wording "noticed".
